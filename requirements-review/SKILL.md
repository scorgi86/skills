# Requirements Review

Оценивать только достаточность требований для начала разработки. Не анализировать код, архитектуру, сроки, трудоёмкость, тест-план или готовность к финальной приёмке.

Не изменять исходные требования.

## Запросить режим

Если режим или точный объём не указан, до анализа предложить `standard` как режим по умолчанию и запросить явное подтверждение:

> Предлагаю режим `standard`: проверить описание задачи, БФТ и обязательные связанные источники с подготовкой Карточки. Подтвердите `standard` либо выберите `fast` или `full`.

Предложить:

1. `standard` — **Стандартная (рекомендуется):** проверить описание задачи, БФТ и обязательные связанные источники; подготовить Карточку.
2. `fast` — **Быстрая:** проверить один основной источник только на очевидные проблемы; вывести предварительный результат без Карточки и нормативного заключения.
3. `full` — **Полная:** проверить все предоставленные и заявленные источники, включая междокументные связи; подготовить Карточку.

Рекомендованный по умолчанию `standard` не является выбранным режимом: не начинать анализ и не фиксировать `mode=standard` до явного подтверждения пользователя. Не спрашивать повторно, если режим уже указан.

## Выполнить этапы

1. До построения любого candidate полностью прочитать `references/development-conclusion-rules.md`, `references/report-schema.md`, `references/review-checklist.md`, `workflows/01-intake.md`, `workflows/06-report.md` и `workflows/07-validate.md`; зафиксировать их revisions для policy snapshot.
2. Применить `workflows/01-intake.md`; определить состояние, режим, основной источник, достаточность входов и тип ожидаемого результата.
3. Если intake определил `INPUT_REQUEST`, пропустить этапы 02–05, построить candidate по уже загруженному `workflows/06-report.md`, проверить его по уже загруженному `workflows/07-validate.md`, после успешной проверки отрендерить и остановиться.
4. Для `standard` и `full` прочитать `workflows/02-map.md`; построить реестры источников, карту требований и source gate, обработать каждый доступный `IN_SCOPE` источник до `REVIEWED` либо зафиксировать причину незавершённости.
5. Прочитать `workflows/03-completeness.md`; проверить только достаточность требований для начала разработки.
6. Для `standard` и `full` прочитать `workflows/04-consistency.md`; проверить доказательства, противоречия и зависимости.
7. Для `standard` и `full` прочитать `workflows/05-findings.md`; сформировать замечания и проекты допущений.
8. До построения candidate зафиксировать revisions всех дополнительно применённых workflows.
9. Для `fast` перейти из `workflows/03-completeness.md` сразу к `workflows/06-report.md`.
10. По уже загруженному `workflows/06-report.md` построить candidate результата, но не выводить его.
11. По уже загруженному `workflows/07-validate.md` проверить candidate и предполагаемый переход состояния.
12. При провале повторить зависимые этапы. Только после успешной проверки отрендерить candidate по `workflows/06-report.md`.

Если любой этап после intake обнаружил обязательный недоступный вход и перевёл выполнение в `AWAITING_INPUT`, немедленно применить ветку `INPUT_REQUEST`: прекратить анализ, пропустить оставшиеся аналитические этапы, построить и проверить запрос входов.

## Контракты режимов

- `fast` использует только явно выбранный основной источник, не расширяет корпус по внешним ссылкам, называет найденное кандидатами на замечания и всегда предупреждает, что полнота требований не подтверждена.
- `standard` включает основной текст, БФТ и каждый источник, необходимый для толкования обязательного поведения.
- `full` включает все предоставленные и заявленные источники; исключение допустимо только при доказанном отсутствии связи с проверяемыми требованиями.
- Только `standard` и `full` могут формировать Карточку, и только при закрытом source gate.

## Ключевые ограничения

- Использовать нормативные заключения, статусы и их инварианты только из `references/development-conclusion-rules.md`.
- Не дублировать и не переопределять нормативные правила в других файлах.
- Не смешивать техническую недоступность источника с подтверждённым недостатком комплекта требований.
- Формировать Карточку только по `references/report-schema.md`; служебную оболочку держать снаружи.
