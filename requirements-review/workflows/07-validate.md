# 07 — Validate

Проверять в следующем порядке.

## 1. Состояние и тип результата

- `AWAITING_MODE` и `AWAITING_INPUT` совместимы только с `INPUT_REQUEST`.
- `DELIVERED` совместим с `FAST_RESULT`, `CARD_DRAFT` или `CARD_OFFICIAL`.
- Причина `INPUT_REQUEST`, режим и `requestedItems` соответствуют контракту `workflows/01-intake.md`.
- `modeState=UNSELECTED` допускает только `MODE_REQUIRED`.

## 2. Оболочка

- `INPUT_REQUEST` и `FAST_RESULT` не содержат Карточку.
- `CARD_DRAFT` и `CARD_OFFICIAL` содержат Карточку и полный `reviewContext`.
- Служебные notices и context находятся вне Карточки.
- Официальная Карточка не содержит содержательных предупреждений.

## 3. Snapshot и актуальность

- snapshot существует и неизменяем;
- для любого `INPUT_REQUEST` фиксирует всё известное состояние; основной источник может отсутствовать;
- для `FAST_RESULT` содержит выбранный основной источник;
- для `CARD_DRAFT` и `CARD_OFFICIAL` перечисляет полный requirement source registry;
- правила snapshot выбраны сначала по `artifactType`, затем по режиму;
- `PRIMARY_SOURCE_REQUIRED` используется только при отсутствующем или неразрешённом основном источнике;
- revisions источников, доказательств, допущений и политик совпадают с использованными;
- каждая вычисляемая revision имеет формат `sha256:<64 строчных шестнадцатеричных символов>` и получена способом из `workflows/02-map.md` или `workflows/06-report.md`;
- `runSnapshotId` уникален в пределах `reviewCaseId`, а snapshot принадлежит текущему `runId`;
- после выдачи snapshot не изменён; при изменении зависимости создан новый run, snapshot и artifact;
- для Карточки snapshot содержит хеш значения автора, признак шаблона и revision события автора, если она известна;
- изменение автора делает прежний artifact устаревшим и требует нового run;
- устаревший artifact не является текущим;
- supersession не пересекает разные `reviewCaseId`.

При несовпадении зависимости сначала выполнить инвалидацию и пересчёт, затем продолжить проверку.

## 4. Доказательные ссылки

- ссылка разрешается в соответствующем реестре;
- запись существует и активна;
- тип и revision совпадают;
- statement доказательного события не дублируется в ссылке;
- `confirmationEvidenceRef` содержит идентификатор и revision события;
- подтверждение допущения относится одновременно к текущей revision события и текущей revision допущения;
- новая revision события не наследует прежнее подтверждение.

## 5. Source gate

- для любой Карточки gate закрыт;
- resolutions совместимы со scope и availability;
- каждый источник с `IN_SCOPE + AVAILABLE` имеет `REVIEWED` и `reviewEvidence` с совпадающим `contentRevision`;
- `reviewEvidence` подтверждает разбор всех доступных частей источника и передачу новых ссылок в реестр;
- для `DELEGATED_EXTRACTION_VERIFIED` подтверждена проверка результата основным агентом;
- макет по ссылке, обязательный для поведения или результата, не имеет `REVIEWED` без зафиксированного доступного среза содержимого;
- `reviewContext` полностью и без пересечений покрывает закрывающие resolutions;
- `PENDING_REVIEW` и `INPUT_REQUIRED` в контексте Карточки отсутствуют.
- при использовании сохраняемого состояния `scripts/review_state.py validate-map` завершился с кодом 0 для данных текущего run.
- при использовании сохраняемого состояния `scripts/review_state.py issue-artifact` подтвердил актуальность policy revisions перед выпуском Карточки.
- для `CARD_OFFICIAL` скрипт подтвердил заполненного автора и действующие confirmation evidence каждого допущения.

## 6. Карточка

- структура соответствует `references/report-schema.md`;
- заключение, статусы и их совместимость проверены по `references/development-conclusion-rules.md`;
- каждое замечание связано с требованием и доказательствами;
- противоречие содержит минимум две независимые текстовые ссылки;
- замечание об отсутствии источника имеет полный набор доказательств;
- запрещённые разделы отсутствуют.

## 7. Черновая и официальная Карточка

- шаблонное поле автора или неподтверждённое допущение допускаются только в `CARD_DRAFT`;
- `CARD_OFFICIAL` имеет заполненное поле автора и действующие подтверждения всех допущений;
- подлинность имени, роль и полномочия автора не проверяются.

Повторять только проваленные и зависимые этапы, если snapshot остальных входов остаётся актуальным.

Не рендерить candidate и не применять предполагаемый переход состояния до успешного завершения всех проверок. После успеха вернуть управление в `workflows/06-report.md` для рендеринга и фиксации нового состояния.
