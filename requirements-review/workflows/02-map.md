# 02 — Map

Использовать этот этап только для `standard` и `full`.

## Скриптовое состояние

Для сохраняемой проверки вести реестр через `scripts/review_state.py` в явно выбранном `--state-dir`. Скрипт является авторитетным хранилищем revisions, source gate, snapshots и artifacts; не дублировать их вручную в диалоге. Скрипт не оценивает требования: основной агент определяет scope, обязательность источника, полноту разбора и замечания.

Использовать маршрут:

```text
init-case → add-evidence/add-source/update-source → mark-reviewed → validate-map
```

- `add-source` создаёт запись источника, вычисляет revision доступного файла и назначает начальный resolution.
- `add-evidence` создаёт или обновляет доказательное событие с текущей revision; использовать его до ссылки на событие из источника, snapshot или подтверждения допущения.
- `update-source` использовать, когда пользователь предоставил ранее недоступный источник, заменил его содержимое или изменил observation; не создавать новый sourceId вместо существующего.
- Перед `mark-reviewed` зарегистрировать все обнаруженные ссылки через `add-source`.
- `mark-reviewed` фиксирует reviewEvidence; основной агент выполняет его только после содержательной проверки.
- При ненулевом завершении `validate-map` не переходить к этапу 03: исправить перечисленные нарушения либо запросить недостающий вход.

## Реестр источников требований

Для каждого обнаруженного источника хранить:

```text
sourceId
displayName
discoveryRef
scope
availability
contentRevision?
observationRevision
reviewEvidence?
```

`contentRevision` обязателен для доступного содержимого. Формировать его как `sha256:<hex>`:

- для файла — SHA-256 его исходных байтов;
- для вставленного текста — SHA-256 UTF-8 текста без изменения символов, кроме нормализации переводов строк в `LF`.

Не использовать дату, имя файла или номер сообщения как `contentRevision`. Если содержимое недоступно, не создавать `contentRevision`.

`observationRevision` обязателен всегда. Формировать его как SHA-256 канонической UTF-8 записи `sourceId`, `scope`, `availability` и причины или ссылки на наблюдение; нормализовать переводы строк в `LF`. При изменении любого из этих значений создавать новую revision.

Значения `scope`:

- `IN_SCOPE`;
- `OUT_OF_SCOPE_BY_MODE`;
- `OUT_OF_SCOPE_BY_CONTENT`.

Значения `availability`:

- `AVAILABLE`;
- `NOT_PROVIDED_TO_AGENT`;
- `TECHNICALLY_UNREADABLE`;
- `CONFIRMED_ABSENT_FROM_REQUIREMENTS_PACKAGE`.

## Границы режимов

Для `standard` дополнительные источники, не нужные для толкования обязательного поведения, можно пометить `OUT_OF_SCOPE_BY_MODE` с причиной. Источник обязательного поведения всегда `IN_SCOPE`.

Для `full` значение `OUT_OF_SCOPE_BY_MODE` запрещено. `OUT_OF_SCOPE_BY_CONTENT` допустимо только с доказательством отсутствия связи с проверяемыми требованиями.

## Реестр доказательных событий

Отдельно от источников требований хранить:

```text
evidenceArtifactId
kind: PACKAGE_INVENTORY | USER_EVENT
revision
statement
active
```

Эти события:

- подтверждают состав комплекта или слова пользователя;
- не входят в source gate;
- не расширяют проверяемый корпус;
- не попадают в `reviewContext`.

Для каждого доказательного события вычислять `revision` как SHA-256 канонической UTF-8 записи его `kind`, `statement` и `active`; нормализовать переводы строк в `LF`. При изменении любого поля создавать новую revision.

## Ссылки на требования

Для каждой однозначной части требования хранить:

```text
requirementId?
sourceId
contentRevision
location
textHash
```

Если FR/NFR ID отсутствует, использовать `sourceId`, местоположение и хеш точной формулировки.

Построить карту:

- обязательного пользовательского поведения;
- бизнес-правил;
- наблюдаемых результатов;
- альтернатив и ограничений;
- критериев приёмки;
- потенциальных недостатков.

## Завершение разбора доступных источников

Для каждого источника с `IN_SCOPE + AVAILABLE` выполнить полный разбор до перехода к следующему этапу:

1. Прочитать всё доступное содержимое, включая таблицы, приложения и встроенные ссылки.
2. Внести однозначные требования и их `location` в карту.
3. Добавить каждую новую ссылку в реестр источников и пересчитать её scope и availability.
4. Зафиксировать `reviewEvidence` с текущими `sourceId`, `contentRevision`, перечнем обработанных частей и ссылок, а также способом разбора: `MAIN_READ` или `DELEGATED_EXTRACTION_VERIFIED`.
5. Установить `REVIEWED` только после проверки `reviewEvidence` основным агентом.

Если полный разбор не завершён, оставить `PENDING_REVIEW`. Если причиной является техническая нечитаемость или отсутствие обязательной части источника, перевести источник в `INPUT_REQUIRED` и применить ветку `INPUT_REQUEST`.

Допускается передать извлечение требований субагенту для нескольких независимых источников или объёмного источника. Субагент обязан вернуть `sourceId`, `contentRevision`, обработанные части, требования с location и обнаруженные ссылки. Основной агент проверяет этот результат, ведёт общий реестр и единолично устанавливает `REVIEWED` и закрывает source gate.

## Макеты по ссылкам

Обнаруженную ссылку на макет регистрировать как отдельный источник. Если макет задаёт обязательное пользовательское поведение, данные, ограничения или наблюдаемый результат, пометить его `IN_SCOPE`.

- Для доступного статического экспорта фиксировать `contentRevision` по его байтам.
- Для изменяемого макета по ссылке фиксировать доступное представление: экспорт, версию страницы или иной неизменяемый срез содержимого; одной URL-ссылки недостаточно для `REVIEWED`.
- Если обязательный макет недоступен, запросить доступ, экспорт или скриншоты через `INPUT_REQUIRED`.
- Если макет не влияет на обязательное поведение, исключить его с причиной по правилам scope.

## Source gate

Разрешение источника вычислять из `scope` и `availability`:

```text
IN_SCOPE + AVAILABLE
  -> PENDING_REVIEW
  -> REVIEWED после проверки

IN_SCOPE + NOT_PROVIDED_TO_AGENT
  -> INPUT_REQUIRED

IN_SCOPE + TECHNICALLY_UNREADABLE
  -> INPUT_REQUIRED

IN_SCOPE + CONFIRMED_ABSENT_FROM_REQUIREMENTS_PACKAGE
  -> BLOCKING_FINDING_CREATED

OUT_OF_SCOPE_*
  -> EXCLUDED_WITH_REASON
```

Обычный недостаток внутри просмотренного источника не меняет `REVIEWED`; замечание хранить отдельно.

Gate закрыт, только если каждый обнаруженный источник имеет:

- `REVIEWED`;
- `EXCLUDED_WITH_REASON`;
- `BLOCKING_FINDING_CREATED`.

`PENDING_REVIEW` и `INPUT_REQUIRED` оставляют gate открытым. При открытом gate Карточку не формировать.

Новые ссылки, обнаруженные во время анализа, добавлять в реестр и повторно открывать gate.

`CONFIRMED_ABSENT_FROM_REQUIREMENTS_PACKAGE` разрешено только при явном подтверждении пользователя или проверенном перечне комплекта. Иначе использовать `NOT_PROVIDED_TO_AGENT`.

## Контекст закрытого gate

Для будущего `reviewContext` подготовить непересекающиеся списки:

- `reviewedSources`;
- `excludedSources` с причиной;
- `confirmedAbsentSources` с причиной.

Списки должны полностью покрывать все источники с закрывающим gate resolution.
