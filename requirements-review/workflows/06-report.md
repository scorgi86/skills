# 06 — Report

Сначала построить candidate envelope и предполагаемый переход состояния. Не рендерить результат пользователю до успешного прохождения `workflows/07-validate.md`.

После успешной валидации отрендерить разрешённые человекочитаемые части и применить переход состояния. При провале вернуться только к зависимым этапам.

## Оболочка результата

Внутренне представить результат как:

```text
reviewCaseId
runId
artifactId
supersedesArtifactId?
runSnapshotId
artifactType
reviewContext?
notices[]
card?
```

Служебные идентификаторы не выводить пользователю. Рендерить только необходимые notices, человекочитаемый `reviewContext` и `card`.

Совместимость:

- `INPUT_REQUEST` — без `card`; содержит одну причину и непустой `requestedItems`;
- `FAST_RESULT` — без `card` и нормативного заключения; показывает основной источник и предупреждение об ограниченном охвате;
- `CARD_DRAFT` — обязательно содержит `reviewContext`, notices с причинами черновика и `card`;
- `CARD_OFFICIAL` — обязательно содержит `reviewContext` и `card`; содержательные notices отсутствуют.

Карточку формировать строго по `references/report-schema.md`.

## Быстрый результат

Использовать:

```text
РЕЗУЛЬТАТ БЫСТРОЙ ПРОВЕРКИ

Основной источник: <название>.
Охват: проверены только очевидные недостатки этого источника.

Кандидаты на замечания: <перечень или «не выявлены»>.

Быстрая проверка не подтверждает полную достаточность требований.
Для Карточки Заключения Разработки требуется режим standard или full.
```

Внешние ссылки основного текста перечислить как ограничения охвата, не как замечания.

## Карточка

Только `standard` и `full` при закрытом source gate могут сформировать Карточку.

Выбрать заключение по `references/development-conclusion-rules.md`.

Использовать `CARD_DRAFT`, если:

- поле автора равно точному шаблонному значению;
- хотя бы одно допущение не имеет действующего подтверждения.

Для черновика вывести перед Карточкой:

```text
ЧЕРНОВИК
```

И краткие причины черновика.

`CARD_OFFICIAL` требует закрытый gate, заполненное поле автора, действующие подтверждения всех допущений и успешную валидацию. Подлинность имени, роль и полномочия не проверяются.

## Review context

Перед каждой Карточкой кратко показать:

- режим;
- проверенные источники;
- исключённые источники и причины;
- подтверждённо отсутствующие источники и причины.

Контекст находится вне Карточки. Его три списка должны быть непересекающимися и полностью покрывать закрывающие resolution source gate.

## Snapshot зависимостей

Snapshot — внутренний структурированный объект текущего `reviewCaseId` и `runId`. Не выводить его пользователю и не создавать для него отдельный файл. Хранить его в рабочем контексте диалога до выдачи следующего актуального результата.

Для каждого результата создать новый неизменяемый snapshot:

```text
modeState
mode?
primarySourceId?
requirementSources[]
evidenceArtifacts[]
assumptions[]
policyRevisions[]
```

`runSnapshotId` должен однозначно идентифицировать snapshot в пределах `reviewCaseId`; допустим последовательный идентификатор `snapshot-<runId>`. После выдачи результата snapshot не редактировать. При новом входе или изменении зависимости создать новый `runId`, новый snapshot и новый artifact; прежний snapshot оставить основанием устаревшего artifact.

Если рабочий контекст диалога недоступен или утрачен, не пытаться восстановить прежний snapshot по памяти: создать новый run, заново собрать доступные входы и выдать новый artifact.

При использовании сохраняемого состояния создавать и проверять snapshot через `scripts/review_state.py snapshot`; передавать в него evidence refs, автора, revisions допущений и их confirmations. Выпуск Карточки регистрировать через `scripts/review_state.py issue-artifact`. Перед созданием snapshot выполнить `scripts/review_state.py validate-map`: при ненулевом завершении не продолжать к report. Скрипт дополнительно сверяет policy revisions и доказательные события перед выпуском artifact.

Snapshot включает:

- для любого `INPUT_REQUEST` — только всё известное на момент запроса состояние; `primarySourceId` необязателен;
- для `FAST_RESULT` — выбранный основной источник и его текущую revision;
- для `CARD_DRAFT` и `CARD_OFFICIAL` — каждую запись полного requirement source registry;
- revisions всех использованных доказательных событий;
- revisions допущений и их подтверждений;
- revisions нормативных правил, схемы, чек-листа и применённых workflow.

Для текста допущения вычислять его `revision` тем же способом, что и для вставленного текста источника в `workflows/02-map.md`. Для каждого применённого policy/workflow файла вычислять revision как SHA-256 исходных байтов файла.

Для `CARD_DRAFT` и `CARD_OFFICIAL` дополнительно включить:

```text
author:
  valueHash
  isPlaceholder
  authorEventRevision?
```

Вычислять `valueHash` как SHA-256 UTF-8 значения автора с нормализацией переводов строк в `LF`. Подлинность имени не проверять. Изменение значения автора делает прежний artifact устаревшим, создаёт новый run и повторяет report и validate.

Правила snapshot выбирать сначала по `artifactType`, а затем по режиму. Не применять требования завершённого `FAST_RESULT` к `INPUT_REQUEST` в режиме `fast`.

`PRIMARY_SOURCE_REQUIRED` требует, чтобы основной источник отсутствовал или оставался неразрешённым.

Каждая запись источника в snapshot содержит:

```text
sourceId
contentRevision?
observationRevision
scope
availability
resolution
```

Включать также исключённые и подтверждённо отсутствующие источники. Изменение любой записи полного registry делает прежний результат устаревшим.

Для `MODE_REQUIRED` использовать `modeState=UNSELECTED` без поля `mode`. Все остальные совместимости режима проверить по `workflows/01-intake.md`.

## Актуальность и замена

`reviewCaseId` идентифицирует одну задачу, `runId` — перерасчёт, `artifactId` — результат.

При изменении зависимости:

- немедленно пометить текущий результат устаревшим;
- очистить текущий artifact до перерасчёта;
- выдать новый результат с новым snapshot;
- при той же задаче связать его с прежним через `supersedesArtifactId`;
- не заменять результаты другого `reviewCaseId`.

При использовании сохраняемого состояния проверять изменения файлов через `scripts/review_state.py invalidate` до повторного анализа. Скрипт переводит изменённый `IN_SCOPE + AVAILABLE` источник в `PENDING_REVIEW`; исчезнувший файл — в `TECHNICALLY_UNREADABLE` и `INPUT_REQUIRED`; затем помечает текущий artifact устаревшим и создаёт новый run.

Текущим является только последний успешно выданный и неустаревший artifact, явно назначенный текущим. Новый `INPUT_REQUEST` также может стать текущим результатом.
