# 01 — Intake

## Модель выполнения

Использовать состояния:

- `START`;
- `AWAITING_MODE`;
- `AWAITING_INPUT`;
- `ANALYZING`;
- `DELIVERED`.

Использовать типы результата:

- `INPUT_REQUEST`;
- `FAST_RESULT`;
- `CARD_DRAFT`;
- `CARD_OFFICIAL`.

Не смешивать состояние выполнения с типом пользовательского результата.

## Начальный маршрут

1. Зафиксировать один `reviewCaseId` для проверяемой задачи или комплекта требований.
2. Если пользователь явно начал проверку другой задачи, создать новый `reviewCaseId`; результаты разных задач не заменяют друг друга.
3. Определить режим:
   - режим отсутствует → предложить `standard` как рекомендуемый режим, перейти в `AWAITING_MODE` и сформировать `INPUT_REQUEST`;
   - режим указан → перейти к проверке входов.
4. Не выбирать режим автоматически: рекомендация `standard` не меняет `modeState` на `SELECTED` и не заполняет `mode` до явного подтверждения пользователя.

В snapshot хранить:

```text
modeState: UNSELECTED | SELECTED
mode?: fast | standard | full
```

Инварианты:

- `UNSELECTED` допускает только `INPUT_REQUEST` с причиной `MODE_REQUIRED`;
- `SELECTED` требует конкретный режим;
- `FAST_RESULT` требует `fast`;
- Карточка требует `standard` или `full`.

## Запрос входов

`INPUT_REQUEST` содержит ровно одну основную причину:

- `MODE_REQUIRED`;
- `SOURCE_REQUIRED`;
- `PRIMARY_SOURCE_REQUIRED`.

И отдельный непустой список `requestedItems`.

Несколько недостающих материалов перечислять в `requestedItems`, не создавать несколько причин.

Совместимость:

- `MODE_REQUIRED` — режим ещё не выбран;
- `PRIMARY_SOURCE_REQUIRED` — выбран `fast`, но основной источник отсутствует или неоднозначен;
- `SOURCE_REQUIRED` — выбран `standard` или `full`, но обязательного входа недостаточно.

## Наличие требований и БФТ

- Нет описания задачи и БФТ → `AWAITING_INPUT` и `INPUT_REQUEST`.
- Формального БФТ нет, но описание доказанно достаточно по `references/review-checklist.md` → использовать описание как основной источник требований.
- БФТ нет и описание недостаточно → `AWAITING_INPUT` и `INPUT_REQUEST`, без Карточки и нормативного заключения.

## Основной источник

Для `fast` определить один `primarySourceId`:

- явно обозначенный пользователем основной текст;
- иначе явно выбранное пользователем описание или БФТ.

Если передано несколько потенциально основных источников и безопасно выбрать нельзя, запросить выбор через `PRIMARY_SOURCE_REQUIRED`.

`fast` анализирует только непосредственно доступное содержимое `primarySourceId`. Ссылки из него на другие материалы фиксировать как ограничения предварительного охвата, но не запрашивать и не превращать в замечания.

## Проверяемый объём

Для `standard` включить описание, БФТ и каждый источник, необходимый для толкования обязательного поведения.

Для `full` включить все предоставленные и явно заявленные источники.

Зафиксировать:

- доступные материалы;
- заявленные, но не переданные материалы;
- технически нечитаемые материалы;
- проверенный перечень комплекта, если он есть.

Не считать непереданный агенту источник отсутствующим в комплекте без явного подтверждения пользователя или проверенного перечня.

## Автор

Не проверять подлинность имени, роль или полномочия автора.

Если имя предоставлено, подставить его в Карточку. Иначе оставить точное шаблонное значение:

```text
<фамилия и имя или полное ФИО>
```

Шаблонное значение делает Карточку черновой, но не останавливает анализ.

## Возобновление

Переходы:

```text
START
  mode absent  -> AWAITING_MODE + INPUT_REQUEST
  mode present -> intake gate

AWAITING_MODE + mode -> intake gate
AWAITING_INPUT + requested input -> intake gate
intake sufficient -> ANALYZING
intake insufficient -> AWAITING_INPUT + INPUT_REQUEST
ANALYZING + newly required input -> AWAITING_INPUT + INPUT_REQUEST
ANALYZING + completed -> DELIVERED
```

При возврате в `AWAITING_INPUT` сохранять режим, реестры, карту и подтверждённые данные. После нового входа повторять только зависимые или проваленные этапы.

Смена режима из любого состояния возвращает выполнение на intake gate и требует пересчёта scope и зависимых результатов.

После `DELIVERED` обрабатывать продолжение явно:

```text
DELIVERED + source/mode/author/assumption/evidence event
  -> invalidate affected derived data
  -> intake gate или ANALYZING
  -> новый artifact
```

- Новый или изменённый источник, режим либо доказательное событие возвращает выполнение на intake gate и повторяет зависимые аналитические этапы.
- Заполнение поля автора или подтверждение неизменного допущения повторяет только report и validate.
- Изменение текста допущения повторяет этапы по правилам `workflows/05-findings.md`.
