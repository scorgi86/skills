# Подготовка плана реализации

Подготовить реализационно пригодный план, который можно передать исполнителю. Не изменять целевой код и другие артефакты реализации. Сохранять сам план в файл только по запросу пользователя.

## Исследование

1. Прочитать требования, связанные спецификации и применимые инструкции репозитория.
2. Исследовать только тот код и те зависимости, которые необходимы для обоснования плана.
3. Отделить явные требования и архитектурные инварианты от предположений, примеров реализации и будущих этапов.
4. Остановиться, если отсутствует продуктовое или архитектурное решение, без которого план нельзя выполнить однозначно.

## Пакет исполнения

Представить пакет в Markdown в сообщении либо сохранить его в файл по запросу пользователя. Точные заголовки и оформление не являются контрактом; обязательна следующая семантика:

- источники требований;
- цель;
- что входит и не входит в работу;
- необходимые изменения и их порядок;
- актуальный DoD с идентификаторами `DOD-1`, `DOD-2` и далее;
- способ проверки каждого пункта DoD;
- открытые блокирующие вопросы;
- риски и условия остановки.

Для каждого пункта DoD определить способ проверки, команду или сценарий, если они известны, и ожидаемый результат. Для дорогой, нестабильной или повторно используемой проверки дополнительно указать проверяемую область и предполагаемые условия, после которых её результат потребуется оценить заново.

Не добавлять несколько проверок одного поведения без отдельного требования или риска, который они подтверждают.

План должен быть достаточен для исполнения без повторного первичного планирования. Не создавать противоречащие или независимо поддерживаемые дубликаты сведений.

Для каждого применимого требования должна быть однозначно прослеживаема связь с необходимым изменением, пунктом DoD и его проверкой. Выбирать форму представления соразмерно задаче; не создавать отдельную матрицу, если связи очевидны из структуры плана.

Найденные ранее замечания могут служить дополнительными доказательствами для существующего пункта DoD либо для пункта, добавленного из пропущенного явного требования. Они не создают отдельный процесс исполнения.

Для архитектурного рефакторинга включить соразмерные критерии отсутствия избыточной сложности.

## Декомпозиция и оценка

Добавлять декомпозицию и оценку трудозатрат только по явному запросу пользователя и после определения цели, границ, необходимых изменений, DoD и проверок. Если запрошено независимое ревью, включить декомпозицию и оценку в проверяемый план. После изменений технического плана, влияющих на состав или объём работ, актуализировать оценку перед повторным ревью.

Каждая работа должна иметь один проверяемый результат, но не обязана соответствовать отдельному файлу или мелкой технической операции. Для каждой работы указать:

- идентификатор;
- результат;
- диапазон трудозатрат в человеко-часах, например `6–10 ч`;
- зависимости через идентификаторы других работ;
- уверенность оценки;
- способ проверки результата.

Рекомендуемая форма — компактная Markdown-таблица. Это не жёсткий контракт: выбирать другое представление, если оно яснее для конкретной задачи. При необходимости после декомпозиции кратко указать существенные допущения и ограничения параллельной работы.

В оценку включать необходимое изучение локального контекста, реализацию, тесты, интеграцию, ожидаемые исправления, обязательные ревью и документацию. Не включать внешнее ожидание, если оно не является выполняемой работой. Общий диапазон трудоёмкости получать суммированием нижних и верхних оценок; не представлять его как календарный срок без данных о составе команды, доступности участников и ограничениях параллельной работы.

Если неизвестность блокирует выбор технического подхода или границы всей работы, остановить планирование, не создавать декомпозицию и не рассчитывать общую трудоёмкость. Если неизвестность локальна и не мешает составить остальной план, оформить исследование как обычную работу, а зависимые оценки и общий диапазон пометить предварительными до её завершения и последующей переоценки.

Использовать зависимости для обозначения возможной последовательной и параллельной работы. Не вычислять без отдельной необходимости критический путь, календарный график или формальную модель данных.

## TDD

Если пользователь просит план через TDD, для каждого применимого изменения описать:

1. Проверку требуемого наблюдаемого поведения, которая до реализации должна падать по ожидаемой причине.
2. Минимальное изменение для прохождения проверки.
3. Рефакторинг без изменения поведения.
4. Необходимую регрессионную проверку.

Выбирать подходящий уровень проверки; не требовать unit-тест, если поведение надёжнее проверяется интеграционным, контрактным или сценарным тестом. Фактический запуск падающей проверки относится к исполнению плана.

## Независимое ревью плана

Проводить только по явному запросу пользователя. Перед началом полностью прочитать [references/plan-review.md](references/plan-review.md) и следовать описанному протоколу. Без запрошенного ревью называть план подготовленным, но не независимо принятым.

Этот навык сам не разрешает реализацию и не запускает `task-runner` без отдельного поручения пользователя. Если пользователь явно поручил последовательно подготовить и выполнить план, сначала завершить пакет планировщика, затем применять `task-runner` как отдельный этап.
