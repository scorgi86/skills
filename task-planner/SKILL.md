# Подготовка плана реализации

Подготовить реализационно пригодный план, который можно передать исполнителю. Не изменять целевой код и другие артефакты реализации. Сохранять сам план в файл только по запросу пользователя.

## Исследование

1. Прочитать требования, связанные спецификации и применимые инструкции репозитория.
2. Исследовать только тот код и те зависимости, которые необходимы для обоснования плана.
3. Отделить явные требования и архитектурные инварианты от предположений, примеров реализации и будущих этапов.
4. Остановиться, если отсутствует продуктовое или архитектурное решение, без которого план нельзя выполнить однозначно.

## Пакет исполнения

Представить пакет в Markdown в сообщении либо сохранить его в файл по запросу пользователя. Точные заголовки и оформление не являются контрактом; обязательна следующая семантика:

- источники требований;
- цель;
- что входит и не входит в работу;
- необходимые изменения и их порядок;
- актуальный DoD с идентификаторами `DOD-1`, `DOD-2` и далее;
- способ проверки каждого пункта DoD;
- открытые блокирующие вопросы;
- риски и условия остановки.

План должен быть достаточен для исполнения без повторного первичного планирования. Не создавать противоречащие или независимо поддерживаемые дубликаты сведений.

Для каждого применимого требования должна быть однозначно прослеживаема связь с необходимым изменением, пунктом DoD и его проверкой. Выбирать форму представления соразмерно задаче; не создавать отдельную матрицу, если связи очевидны из структуры плана.

Найденные ранее замечания могут служить дополнительными доказательствами для существующего пункта DoD либо для пункта, добавленного из пропущенного явного требования. Они не создают отдельный процесс исполнения.

Для архитектурного рефакторинга включить соразмерные критерии отсутствия избыточной сложности.

## TDD

Если пользователь просит план через TDD, для каждого применимого изменения описать:

1. Проверку требуемого наблюдаемого поведения, которая до реализации должна падать по ожидаемой причине.
2. Минимальное изменение для прохождения проверки.
3. Рефакторинг без изменения поведения.
4. Необходимую регрессионную проверку.

Выбирать подходящий уровень проверки; не требовать unit-тест, если поведение надёжнее проверяется интеграционным, контрактным или сценарным тестом. Фактический запуск падающей проверки относится к исполнению плана.

## Независимое ревью плана

Проводить только по явному запросу пользователя.

Запустить нового субагента с чистым контекстом и запретом изменять файлы. Передать ему требования, границы, план, применимые инструкции и необходимый исходный контекст. Не передавать выводы автора и ожидаемый вердикт.

Потребовать `PASS` или `FAIL` с доказательствами для:

- покрытия требований;
- отсутствия противоречий;
- реализуемости шагов;
- проверяемости DoD;
- соблюдения границ.

Блокирующими являются только непокрытое входящее требование, противоречие, отсутствующее необходимое решение, нереализуемый шаг, непроверяемый DoD или выход за границы. Остальные замечания зафиксировать как неблокирующие.

Вердикт `PLAN_READY` допустим только при отсутствии блокирующих замечаний. После `PLAN_BLOCKED` исправить обоснованные блокеры, если это не требует отсутствующего пользовательского, продуктового или архитектурного решения. При необходимости такого решения остановиться и запросить его у пользователя. Изменение цели, границ, DoD, архитектурного решения, порядка зависимых шагов или стратегии проверки аннулирует прошлый вердикт и требует нового чистого проверяющего. Редактура и исправление навигации без изменения смысла повторного ревью не требуют.

Выполнить не более трёх проверок. После третьего `PLAN_BLOCKED` остановиться и сообщить оставшиеся блокеры и необходимые решения.

Если субагент недоступен, выполнить строгую самопроверку, явно сообщить об отсутствии независимого ревью и не выдавать `PLAN_READY`. Без запрошенного ревью называть план подготовленным, но не независимо принятым.

Этот навык сам не разрешает реализацию и не запускает `task-runner` без отдельного поручения пользователя. Если пользователь явно поручил последовательно подготовить и выполнить план, сначала завершить пакет планировщика, затем применять `task-runner` как отдельный этап.
