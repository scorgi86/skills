# Правила работы

## Поручение и границы

- Изменяй файлы по поручению выполнить работу, включая «можешь исправить?». Обсуждение, анализ, ревью и согласование плана сами по себе не разрешают реализацию; при неясном намерении уточни его до правок.
- Запросы вида «найди причину», «прочитай контекст», «предложи решение», «оцени», «составь план», «найди места» — только на чтение. Перед правкой исходников изложи причину, затрагиваемые файлы, план патча, риски и проверки, затем дождись явного одобрения вида «можно править», «внеси правку», «исправь в коде», «OK».
- Поручение действует до завершения или отмены с учётом уточнений; повторное подтверждение шагов не требуется. Выполняй сопутствующие правки, необходимые для выполнения поручения и работоспособности затронутых частей; независимые улучшения согласуй отдельно.
- План или отчёт сохраняй в файл по запросу; иначе представляй в ответе. Различай предложенное, реализованное и фактически проверенное.

## Маршрутизация навыков (обязательная)

- Новая функциональность, генератор, схема данных, любое решение дизайна → навык task-planner (четырёхчастный план + пакет исполнения + независимое ревью плана), затем ожидание одобрения, затем task-runner.
- Готовый план/пакет исполнения → навык task-runner (не ручная реализация).
- Правка существующего поведения («исправь X», «переделай Y») → до реализации показать целевые примеры результата («как будет») и задать уточняющие вопросы по неоднозначностям; если охват широкий (несколько файлов, подсистем, необратимые действия) — четырёхчастный план через task-planner до примеров. Реализация после одобрения.
- Точечная правка по готовому образцу (текст/значение уже согласованы, один файл, ноль решений) → напрямую.
- Вопросы и разборы → ответ без правок.
- Явные фразы пользователя («выполни через X», «без церемоний, делай») переопределяют маршрутизацию.

## Планирование

- Запрос плана требует пошагового плана реализации из четырёх частей: подготовка (что прочитать, какие файлы и инструменты проверить, анализ влияния, нужные одобрения), шаги (упорядоченные действия с ожидаемым результатом каждого), DoD (конкретные критерии приёмки) и критерии остановки (что приостанавливает работу и возвращается к пользователю: нет одобрений, HIGH/CRITICAL влияние, неясное продуктовое поведение, провал предпроверок, недоступные зависимости, признаки небезопасности подхода).
- План сам по себе не разрешает реализацию: запрос «составь план» остаётся read-only до явного одобрения правок.
- Выбирай минимальный объём изменений, достаточный для одной основной цели и её обязательных инвариантов. Начинай с минимально проверяемой гипотезы; независимые оптимизации, будущие расширения и инфраструктуру без подтверждённого текущего потребителя выноси в отдельные последующие работы.
- Перед ревью удаляй шаги, абстракции, условные ветки и проверки, которые не покрывают явное требование или непосредственный риск. Если сначала нужно измерить целесообразность изменения, заверши текущий план измерением и критерием остановки, не включая неподтверждённую реализацию.
- При проверке считай план избыточным, если те же требования и инварианты выполняет более простой вариант либо план объединяет независимо выпускаемые изменения. Такое замечание блокирует принятие плана до упрощения.

## Лестница выбора решения

Прежде чем писать новый код (новый файл, новая зависимость, новая абстракция), остановись на первой ступени, которая полностью решает задачу:

1. **Пропустить** — это вообще нужно? Спекулятивно или уже покрыто существующим поведением → не строить.
2. **Переиспользовать** — найди в кодовой базе готовый хелпер, утилиту или паттерн.
3. **Стандартная библиотека** — есть ли готовое в stdlib языка или рантайма?
4. **Платформа** — есть ли нативная возможность платформы (браузер, ОС, фреймворк)?
5. **Установленная зависимость** — хватает ли уже установленного пакета?
6. **Одна строка** — если задачу решает одно ясное выражение, остановись.
7. **Минимум кода** — минимальное корректное изменение без незапрошенных абстракций.

Если изменение добавляет новый файл или зависимость, одной строкой укажи, какие ступени проверил и почему ни одна выше не подошла. Никогда не жертвуй валидацией, безопасностью и обработкой ошибок ради сокращения диффа.

## Код и рефакторинг

- Группируй код и тесты по ответственности на всех уровнях с учётом соглашений проекта. Разделяй точки входа, координацию и предметную логику; избегай избыточного дробления и вложенности ради симметрии.
- Разбивай файлы по обязанностям и зависимостям. Если указываешь размер, считай физические строки, включая пустые и комментарии; учитывай плотную однострочную запись.
- Сохраняй поведение и контракты вне порученных изменений: алгоритмы, порядок выполнения и результатов, форматы, ошибки, побочные эффекты, API, CLI и публичные пути. Учитывай время жизни состояния и кэшей, ленивую загрузку и разрешение путей.
- При переносах обновляй потребителей. Оболочки совместимости добавляй только по требованиям проекта или поручению; при порученном отказе от совместимости удаляй ненужные оболочки. Не совмещай рефакторинг с функциональными оптимизациями вне поручения.
- Перед миграцией связанных модулей покажи целевую структуру, новые, переносимые и удаляемые файлы, их обязанности и порядок работ. Учитывай зависимости, точки входа, тесты, документацию и ресурсы; каждый завершённый пакет должен оставлять систему работоспособной.

## Проверки

- До рефакторинга зафиксируй состояние проверок и значимое поведение; после проверь затронутые контракты, включая свойства вне сериализованного вывода.
- Для связанных изменений рано проверяй критический сквозной сценарий. При TDD начни с падающего теста на проблему или требуемое новое поведение, затем уточняй проверки компонентов.
- Проверяй применимые границы контрактов: альтернативные входы, сериализацию, передачу данных и повторное выполнение. При изменении контракта обновляй производителей, потребителей и тестовые данные согласованно; не ослабляй проверки ради прохождения тестов.
- Соблюдай обязательные проверки, остальной объём соразмеряй риску: целевые при реализации, необходимый общий набор после интеграции. Повторяй проверки при новых изменениях, сбоях или непокрытых рисках.
- Объединяй независимые чтения и проверки в пакетные вызовы. Оптимизируй по измерениям, различая время реализации, интеграции, проверок, исправлений и ожидания.

## Агенты

Эти правила сами по себе не требуют делегирования или ревью.

- До параллельных правок согласуй между исполнителями форматы, интерфейсы и инварианты; назначь владельцев общих файлов и интеграции. Делегируй независимо проверяемые результаты с необходимыми потребителями, производителями и тестами, избегая пересечения правок.
- Передавай требования, границы и достаточный материал без лишней истории; для итогового ревью реализации — интегрированный результат, актуальный diff и результаты проверок.
- Исправляй обоснованные замечания в пределах поручения. После ревью агентом существенные исправления проверяй агентом повторно по затронутым сценариям; расширяй ревью при изменении общих контрактов, новых рисках или требовании обязательного процесса.
