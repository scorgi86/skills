# Контракт результата

## Реестр источников

Для каждого описания и вложения указать `Source ID`, имя/ссылку, версию, статус `прочитан` или `недоступен` и причину пробела. Для связанного, но не переданного материала допустим статус `исключён` с доказательством неприменимости.

## Manifest и Git-контекст

Для каждого заявленного или обнаруженного репозитория указать:

- path и remote без секретов;
- статус `готов`, `исключён`, `не включён`, `ветка отсутствует`, `diff пуст`, `неоднозначная база` или `недоступен`;
- base/head refs и SHA, merge base, время remote query/fetch;
- ограничения выбранного diff.

Только `готов`, `diff пуст` и доказанный `исключён` не блокируют оценку реализации. `diff пуст` означает успешно построенную пустую разницу, а не недоступный diff.

## Реестр требований

| Поле | Содержание |
|---|---|
| ID | `R-001`, `R-002`, ... |
| Requirement | Атомарная формулировка |
| Source | Точный источник |
| Criterion | Наблюдаемое условие выполнения |
| Constraints | Ограничения и исключения |
| Owners | Предполагаемые компоненты и репозитории |

## Матрица покрытия

Для каждого требования указать:

- статус реализации: `реализовано`, `частично реализовано`, `не реализовано`, `реализовано с отклонением`, `невозможно подтвердить` или `не применимо`;
- файлы, символы и объяснение поведения;
- выполненные проверки и изученные статические доказательства;
- достаточность доказательств: `достаточно`, `частично` или `недостаточно`;
- непокрытые ветви и ограничения.

Успешная команда или существующий тест не доказывают полный критерий автоматически. Объяснить, почему совокупность доказательств достаточна.

## Реестр изменений

Для каждого изменённого файла указать repository, path, тип изменения, связанные Requirement IDs или техническое обоснование, статус рассмотрения и проверенные владельцы/получатели. Пустой diff фиксировать на уровне manifest.

## Замечания

Дефект существующей реализации содержит приоритет, Requirement ID или нарушенный контракт, минимальный диапазон строк, достижимый сценарий и последствие.

Пробел реализации содержит Requirement ID, ожидаемое поведение, доказательство отсутствия, предполагаемого владельца и последствие; ссылка на несуществующую строку кода не требуется.

Приоритеты: `P0` — катастрофический эффект; `P1` — блокирующий основной сценарий или серьёзная регрессия; `P2` — значимый дефект в конкретных условиях; `P3` — небольшой подтверждённый дефект.

## Порядок отчёта

Первым элементом без вводного текста вывести H1-заголовок с одним из трёх вердиктов:

- `ПРОХОДИТ ПРОВЕРКУ` — все применимые требования реализованы, доказательства достаточны и подтверждённых дефектов нет;
- `НЕ ПРОХОДИТ ПРОВЕРКУ` — найден подтверждённый дефект, отклонение либо нереализованное требование;
- `ПРОВЕРКА НЕ ЗАВЕРШЕНА` — без доказанного дефекта реализацию невозможно оценить из-за отсутствующего описания задачи, обязательного вложения или доступного для анализа diff.

Использовать шаблон:

```markdown
# <ПРОХОДИТ ПРОВЕРКУ | НЕ ПРОХОДИТ ПРОВЕРКУ | ПРОВЕРКА НЕ ЗАВЕРШЕНА>

Причина: <одно предложение с решающим основанием>.
```

Для `НЕ ПРОХОДИТ ПРОВЕРКУ` выбрать наиболее серьёзное решающее замечание и указать Requirement ID, если он применим. Для `ПРОВЕРКА НЕ ЗАВЕРШЕНА` назвать конкретный отсутствующий вход или доказательство. Для `ПРОХОДИТ ПРОВЕРКУ` использовать основание «все применимые требования реализованы, подтверждённых дефектов не найдено».

Далее вывести:

1. Замечания по убыванию приоритета либо «Доказуемых дефектов не найдено».
2. Источники.
3. Покрытие требований.
4. Изменения вне требований.
5. Выполненные проверки.
6. Ограничения проверки с точными проверенными base/head SHA либо «нет».

Завершить отчёт блоком:

```text
Итог: <ПРОХОДИТ ПРОВЕРКУ | НЕ ПРОХОДИТ ПРОВЕРКУ | ПРОВЕРКА НЕ ЗАВЕРШЕНА>.
Основание: <одно предложение>.
Ограничения: <список либо «нет»>.
```

Верхняя `Причина` и финальное `Основание` должны быть согласованы и указывать на один решающий факт. Верхняя формулировка служит кратким ответом, финальная — формальным резюме.

## Приоритет вердикта

1. Если найден доказанный дефект, использовать `НЕ ПРОХОДИТ ПРОВЕРКУ`, даже когда часть проверки недоступна.
2. Если дефект не доказан, но отсутствует минимально необходимый вход или diff нельзя построить и исследовать, использовать `ПРОВЕРКА НЕ ЗАВЕРШЕНА`.
3. Если все применимые требования реализованы и подтверждённых дефектов нет, использовать `ПРОХОДИТ ПРОВЕРКУ`; необязательные непроведённые проверки перечислить как ограничения.

Недоступность remote сама по себе не меняет вердикт, если проверены точные base/head SHA и diff доступен. Пустой успешно построенный diff не означает незавершённую проверку: отсутствие требуемой реализации ведёт к `НЕ ПРОХОДИТ ПРОВЕРКУ`.
