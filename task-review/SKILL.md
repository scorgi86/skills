# Task Review

Проводить доказательное ревью реализации относительно требований. Не изменять код, рабочее дерево, локальные ветки, историю, требования или вложения.

## Собрать обязательные входы

Определить описание задачи, целевую и базовую ветки, целевые репозитории и все переданные вложения. Описание задачи обязательно: если содержательного описания нет, первой строкой вывести `ПРОВЕРКА НЕ ЗАВЕРШЕНА`, запросить описание и остановиться. Не восстанавливать требования только по названию ветки, коммитам или коду.

Составить реестр источников и полностью прочитать описание и каждое переданное вложение. Недоступный источник не считать прочитанным. Связанный, но не переданный материал можно исключить только с записанной причиной; переданное вложение исключать нельзя.

## Зафиксировать Git-снимок

Для каждого репозитория:

1. Проверить path, remote, status и заявленные refs.
2. Подтвердить base/head через authoritative remote query; stale tracking ref не является подтверждением.
3. Точечно загрузить нужные объекты без prune, tags и изменения несвязанных refs.
4. Зафиксировать base SHA, head SHA, merge-base SHA и время получения.

Не выполнять `pull`, `checkout`, `switch`, `merge`, `rebase`, `reset`, очистку или иные операции, меняющие рабочее дерево либо историю. Не включать незакоммиченные изменения без явного указания пользователя. Если актуальность refs не подтверждена, сообщить об этом и не выдавать локальный снимок за последний.

Сформировать manifest заявленных репозиториев. Если требования или код указывают на обязательный репозиторий вне scope, запросить его включение либо доказуемое исключение; до разрешения вопроса блокировать полный verdict.

## Построить требования и объём изменений

Перед оценкой кода прочитать [контракт результата](references/review-contract.md). Атомизировать требования, присвоить ID и указать источник, наблюдаемый критерий, ограничения и предполагаемых владельцев. Предположения и конфликты не превращать в требования.

Для каждого репозитория анализировать итоговый diff всей ветки:

```text
git diff <merge-base>..<head>
```

Построить реестр всех добавленных, изменённых, удалённых и переименованных файлов, включая тесты, конфигурацию, миграции, схемы и ресурсы. Каждый элемент отметить как рассмотренный либо указать причину пробела.

Если base tip отличается от merge base, есть частичная интеграция, rewrite, revert, подозрение на опубликованный секрет/миграцию или запрос на аудит истории, прочитать [правила истории и интеграции](references/git-history.md). В обычном ревью не заявлять форензическую полноту недостижимой истории.

## Выполнить семантическое и техническое ревью

Проверять трассировку в обе стороны:

```text
требование -> реализация -> доказательство
изменение -> требование, техническая необходимость или выход за scope
```

Для каждого требования установить статус реализации и достаточность доказательств. Проверять фактическое поведение: условия, состояния, ошибки, сохранение данных, совместимость и взаимодействие репозиториев.

Исследовать определения и релевантных получателей изменённого поведения. Для публичных API, форматов, схем, сериализации, persistence, config keys, feature flags и межрепозиторных контрактов прочитать [правила семантической инвентаризации](references/semantic-inventory.md).

Проверить correctness, регрессии, потерю данных, безопасность, совместимость, граничные состояния, конкурентность, производительность, миграции и тесты. Сообщать только доказуемые дефекты с достижимым сценарием и последствием; стилистические предпочтения дефектами не считать.

Запускать проверки только когда это необходимо и безопасно. Перед любым запуском прочитать [правила безопасной верификации](references/safe-verification.md). Существование теста не означает, что поведение проверено.

## Сформировать результат

Следовать [контракту результата](references/review-contract.md). Начать отчёт H1-заголовком с одним из трёх вердиктов:

- `ПРОХОДИТ ПРОВЕРКУ` — в проверенном снимке все применимые требования реализованы и подтверждённых дефектов нет;
- `НЕ ПРОХОДИТ ПРОВЕРКУ` — найден подтверждённый дефект, отклонение либо нереализованное требование;
- `ПРОВЕРКА НЕ ЗАВЕРШЕНА` — без доказанного дефекта реализацию нельзя оценить из-за отсутствующего описания, обязательного вложения или доступного для анализа diff.

Сразу после заголовка дать `Причина: <одно предложение>` с решающим основанием. Для отрицательного результата сослаться на наиболее серьёзное замечание и Requirement ID, если он применим; для незавершённой проверки назвать конкретный отсутствующий вход или доказательство. Верхняя причина и финальное основание должны описывать один и тот же решающий факт.

Доказанный дефект имеет приоритет над ограничениями: при одновременно найденном дефекте и неполной проверке использовать `НЕ ПРОХОДИТ ПРОВЕРКУ`, а неполноту перечислить отдельно.

Не считать пустой, но успешно построенный diff недоступным. Если задача требует изменения ветки, их отсутствие является нереализованным требованием; если требование уже выполнено вне diff, оценивать это только в пределах явно согласованного scope.

Недоступность remote, отсутствие необязательного ручного теста и другие ограничения не заменяют основной вердикт, если точные проверенные base/head SHA и diff доступны. Перечислить их в разделе `Ограничения проверки` с точными SHA.
