# Recipient Fan-out

Fan-out нужен, когда целевая сущность является свойством, контейнером или частью shared model. В этом случае главный риск - найти только один объект, хотя изменение затронет все семейства получателей.

## Как Искать Получателей

1. Найди контейнер или владельца, через который целевая сущность попадает в другие объекты.
2. Проследи реальные типы владельцев, включая поля с другими именами, массивы эффектов, вложенные контейнеры и конкретных наследников общего base class. Проверяй типизированные producer/reader bindings и dispatch, а не только совпадение имени свойства.
3. Для каждого типа проверь отдельные пути:
   - creation/defaults;
   - user/API mutation;
   - import/deserialization;
   - recalculation/cache;
   - property readback/resolution;
   - rendering/preview;
   - export/serialization;
   - copy/paste;
   - tests/fixtures.
4. Отметь, где путь общий, а где расходится по типу объекта.

Сохраняй операции и bindings в существующих typed facts по мере обнаружения на этапах 1–5, не восстанавливай матрицу из памяти при финальном отчёте. Общий механизм доказывай один раз, затем связывай с каждым конкретным семейством через владение/наследование и отдельные exceptions. Для storage, mutation, readback, render и persistence указывай доказанный путь либо конкретное scoped limitation; наличие storage или generic serializer не доказывает остальные пути. Различай writer→container→mapper и reader bindings для каждого протокола.

## Вопросы Полноты

- Есть ли общий base class или interface, который скрывает реальные получатели?
- Есть ли dispatch по object type в render/export/serializer?
- Есть ли объекты, которые хранят свойство, но игнорируют его при output?
- Есть ли fallback/default, который применяется только к части получателей?
- Есть ли продуктовые слои, где сценарий общий, но bridge разный?
- Есть ли fixtures, где сущность присутствует только как persisted data?
