# Направления оптимизации task-research

Обновлено: 2026-09-11 по итогам профилирования и сравнительного прогона исследования внутренних теней.

Статус: выполненные направления подтверждены указанными проверками и замерами. P1–P3 остаются кандидатами, а не поручением на реализацию; перед доработкой повторно проверять актуальное узкое место.

## Архитектурные решения

### JSON-модель и отчёты

Целевая последовательность: факты → JSON-модель → проверка структуры и смысла → Markdown.

JSON Schema проверяет обязательные поля, типы и допустимые статусы. Смысловой валидатор проверяет разрешимость evidence-ссылок, полноту покрытия, основания для отсутствия использований и согласованность выводов. Одной JSON Schema недостаточно.

Реализовано: Stage 7 формирует report-model, Stage 8 связан с её digest, а модель и bundle-проекция проходят отдельные проверки. Markdown не используется как переходный вход и не является источником фактов. Разбор Markdown сохранять только при появлении отдельного сценария импорта старых или вручную отредактированных отчётов.

Следующая проверка полноты должна оценивать семантическое покрытие отдельно от числа evidence. Большой индекс совпадений не компенсирует потерю пользовательских и технических сценариев, явных checked-no-usage, раздельных продуктовых пробелов и существующих точек изменения. `coverage: complete` допустим только когда для каждой применимой capability есть содержательный результат: подтверждённый путь, доказанное отсутствие либо явно обоснованное N/A. Для задачи доработки модель должна связывать пробелы с конкретными implementation entry points; отсутствие таких точек нельзя скрывать переводом capability в необязательный `reference-only`.

Регрессионный эталон для внутренних теней — комплект от 30 июля 2026 года: 4 сценария, 5 critical paths, 3 раздельных пробела, 5 точек реализации и явные отрицательные результаты. Новый отчёт должен сохранять этот смысловой минимум и может расширять его более подробными source anchors. Сравнение полноты выполнять по нормализованным категориям и связям, а не по размеру Markdown или количеству evidence.

### Два уровня инкрементальности

1. Переиспользование файлового анализа: неизменённый файл не парсится повторно, запросы и итоговые проверки выполняются заново.
2. Переиспользование фактов: пересчитываются зависимые выводы; необходимы снимок области поиска и явные правила инвалидирования.

Сначала реализовать первый уровень. Для второго учитывать изменения scope, запросов, настроек и версий анализа наряду с изменениями файлов. Закрытые артефакты сохранять неизменными; новый запуск получает новую ревизию с происхождением переиспользованных данных. Кешированные AST-кандидаты сами по себе не становятся source-confirmed evidence.

### Разделение файлов

Реализовано: файловый анализ, кеш, evidence, модель отчёта, renderer, state и pipeline разделены по самостоятельным обязанностям. `stage_pipeline.js` и `stage8_runner.js` не дробились ради размера.

Сохранять CLI и экспорты через прежние точки входа; передавать зависимости явно, избегать циклических импортов и общего `utils.js` без конкретного назначения. Новое извлечение модулей делать только при появлении самостоятельной причины изменения.

## Последовательность и критерии приёмки

Выполнены файловый и query-кеши AST, параллельный анализ, маршрутизация тёплого batch, source snapshots, однократная финализация Stage 2 и переиспользование исходников при report validation. Pipeline переиспользует AST между Stage 1 и Stage 2 и выполняет канонизацию Stage 2 один раз. Методика воспроизводимого сравнения: [benchmark-methodology.md](benchmark-methodology.md). Старые оценки без сохранённого baseline runtime не используются для решений.

Benchmark запускается командой `npm run benchmark:stages -- --runtime <skill-root> --requests <request-pack.json> --output <result.json> --warmup 1 --runs 3`. Для сравнения добавляется `--compare <baseline.json>`. Сравнение отклоняет несовпадающие harness, requests, environment, target repositories и семантические результаты.

Отдельный A/B общего AST-кеша на запросе «исследуй все о внутренних тенях» использует две серии, по одному прогреву и шесть измеряемых пар на версию. Порядок baseline/current чередуется и меняется между сериями. Сохранены полный workload, Git-состояние целевых репозиториев, environment и implementation digests, времена Stage 1/2 с разложением AST/evidence/residual, cache hit/miss и семантические digests. Методика и результат: [internal-shadows-shared-cache-ab-20260909.md](benchmarks/internal-shadows-shared-cache-ab-20260909.md).

Принимать оптимизации по сохранению содержательных результатов, evidence-ссылок и статусов полноты при сравнении полного и оптимизированного запусков. Проверять неизменённый повторный запуск, изменение файла, добавление использования в новом файле, удаление, переименование, незакоммиченные изменения и изменение настроек анализа. При ошибках парсинга или усечении сохранять неизвестность и ограничения, не превращать их в доказательство отсутствия.

Профиль после query-cache и source snapshot показал, что `prepareFacts` занимает 11,28 мс на Stage 1 и 24,78 мс на Stage 2. В тёплом Stage 1+2 доминировал AST-путь: 2,44–2,63 с из общих 2,84–3,00 с, хотя `runQuery` уже не выполнялся. Детальный cache-hit профиль показал, что source read и identity занимают менее 6 мс на стадию, а загрузка, JSON-разбор и валидация 30–31 МиБ file-cache entries — 462–490 мс. Реализован batch-level выбор: полностью тёплый набор идёт последовательно, mixed/cold — в прежний worker pool. Формальный A/B подтвердил warm-ускорение 20,98–27,96% без превышения 10% regression gate для mixed/cold. Данные: [canonicalization profile](benchmarks/internal-shadows-canonicalization-profile-20260910.md), [residual profile](benchmarks/internal-shadows-residual-profile-20260910.md), [AST cache-hit profile](benchmarks/internal-shadows-ast-cache-hit-profile-20260910.md) и [routing A/B](benchmarks/internal-shadows-parallel-ast-routing-20260910.md).

Последний профиль перенёс основной приоритет с повторной source validation на качество итоговой модели. После оптимизации проверка 599 evidence использует 22 чтения. Следующее изменение производительности выбирать только после нового профиля полного запуска; локальные выигрыши порядка долей секунды не являются самостоятельным приоритетом.

Для декомпозиции проверять сохранение внешних интерфейсов и поведения. Для JSON-валидации — перенос существующих смысловых правил и сохранение обязательной информации при рендеринге. Зафиксированные рекомендации не вводят новые требования в текущий runtime до отдельной реализации.
