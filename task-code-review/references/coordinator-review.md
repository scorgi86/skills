# Полное ревью координатора

Исполнитель отвечает за все заявленные требования, весь согласованный scope и итоговый пользовательский вердикт. Делегирование отдельных срезов не передаёт эту ответственность.

## Собрать обязательные входы

Определить описание задачи, целевую и базовую ветки, целевые репозитории и все переданные вложения. Описание задачи обязательно: если содержательного описания нет, первой строкой вывести `ПРОВЕРКА НЕ ЗАВЕРШЕНА`, запросить описание и остановиться. Не восстанавливать требования только по названию ветки, коммитам или коду.

Составить реестр источников и полностью прочитать описание и каждое переданное вложение. Недоступный источник не считать прочитанным. Связанный, но не переданный материал можно исключить только с записанной причиной; переданное вложение исключать нельзя.

## Зафиксировать Git-снимок

Для каждого репозитория:

1. Проверить path, sanitized canonical remote, status и заявленные refs.
2. Подтвердить base/head через authoritative remote query; stale tracking ref не является подтверждением.
3. Точечно загрузить нужные объекты без prune, tags и изменения несвязанных refs.
4. Зафиксировать полные base SHA, head SHA, merge-base SHA и время получения.

После фиксации authoritative boundaries использовать `snapshot` из [автоматизированного fast path](automation.md), если он доступен. Принять возвращённые boundaries и `changed_files` как результат структурной проверки и не повторять вручную проверку существования объектов, построение inventory или сортировку paths без конкретного противоречия. CLI не заменяет проверку repository identity и remote freshness.

Не выполнять `pull`, `checkout`, `switch`, `merge`, `rebase`, `reset`, очистку или иные операции, меняющие рабочее дерево либо историю. Не включать незакоммиченные изменения без явного указания пользователя. Если актуальность refs не подтверждена, сообщить об этом и не выдавать локальный снимок за последний.

Сформировать manifest заявленных репозиториев. Если требования или код указывают на обязательный репозиторий вне scope, запросить его включение либо доказуемое исключение; до разрешения вопроса блокировать полный verdict.

## Построить требования и объём изменений

Атомизировать требования, присвоить ID и указать источник, наблюдаемый критерий, ограничения и предполагаемых владельцев. Предположения и конфликты не превращать в требования.

Для каждого репозитория анализировать итоговый diff всей ветки. При успешном `snapshot` использовать его boundaries и полный `changed_files`; содержимое релевантных изменений читать из зафиксированного diff. В ручном fallback построить diff:

```text
git diff <merge-base>..<head>
```

Построить реестр всех добавленных, изменённых, удалённых и переименованных файлов, включая тесты, конфигурацию, миграции, схемы и ресурсы. Каждый элемент отметить как рассмотренный либо указать причину пробела.

## Выполнить семантическое и техническое ревью

Сначала выполнить маршрутизацию: связать requirements с changed files, определить затронутые компоненты, применимые категории риска и необходимость consumer search или делегирования. Затем исследовать выбранные пути до наблюдаемой границы поведения. Не выполнять одинаково глубокую проверку категории без сигнала из требования, diff, контракта или найденного consumer.

Проверять трассировку в обе стороны:

```text
требование -> реализация -> доказательство
изменение -> требование, техническая необходимость или выход за scope
```

Для каждого требования установить статус реализации и достаточность доказательств. Проверять фактическое поведение: условия, состояния, ошибки, сохранение данных, совместимость и взаимодействие репозиториев.

Проверить correctness, регрессии, потерю данных, безопасность, совместимость, граничные состояния, конкурентность, производительность, миграции и тесты. Стилистические предпочтения дефектами не считать.

## Делегирование

Делегирование опционально. Для каждого делегата сформировать и до отправки проверить packet по [контракту делегированного ревью](delegated-review.md). Packet содержит уникальные `assignment_id` и `repository_id`, repository-qualified file/code/inspection/search refs, tagged source refs, непустые requirements и assignment scope, immutable snapshot boundaries и optional metadata materialized diff. Не передавать duplicate Requirement IDs, repository IDs или exact refs. В handoff связывать findings и scope structures с каноническими Requirement IDs, не подменяя их source provenance.

Не делегировать небольшой связный срез только ради использования delegated mode. Для fast path без `materialized_diff` вызвать `validate-packet` до отправки. После получения handoff вызвать `validate-handoff`; при успехе не повторять schema/ref/snapshot/status checks и проверить только истинность evidence, достижимость сценария, существенные findings и полноту глобального scope.

Координатор обязан:

- обеспечить покрытие всех требований и изменённых файлов;
- обработать `scope_requests` и при необходимости выдать новый packet;
- сопоставить локальные finding keys, устранить дубликаты и противоречия;
- агрегировать evidence без потери `repository_id` и различать одинаковые paths из разных repositories;
- назначить глобальные Finding IDs;
- объединить ограничения и проверить полноту всего scope;
- самостоятельно применить правила глобального вердикта.

Handoff делегата является доказательством по назначенному срезу, а не итоговым вердиктом задачи.

Вести единое внутреннее состояние ревью и записывать полное evidence один раз в requirement status или finding. Переиспользовать одинаковый отрицательный search scope для нескольких Requirements. Пользовательский отчёт формировать после закрытия requirements, changed files и handoffs, а не использовать его как промежуточный рабочий реестр.

## Контракт полного результата

### Реестр источников

Для каждого описания и вложения указать `Source ID`, имя/ссылку, версию, статус `прочитан` или `недоступен` и причину пробела. Для связанного, но не переданного материала допустим статус `исключён` с доказательством неприменимости.

### Manifest и Git-контекст

Для каждого заявленного или обнаруженного репозитория указать:

- path и remote без секретов;
- статус `готов`, `исключён`, `не включён`, `ветка отсутствует`, `diff пуст`, `неоднозначная база` или `недоступен`;
- base/head refs и SHA, merge base, время remote query/fetch;
- ограничения выбранного diff.

Только `готов`, `diff пуст` и доказанный `исключён` не блокируют оценку реализации. `diff пуст` означает успешно построенную пустую разницу, а не недоступный diff.

### Реестр требований

| Поле | Содержание |
|---|---|
| ID | `R-001`, `R-002`, ... |
| Requirement | Атомарная формулировка |
| Source | Точный источник |
| Criterion | Наблюдаемое условие выполнения |
| Constraints | Ограничения и исключения |
| Owners | Предполагаемые компоненты и репозитории |

### Матрица покрытия

Для каждого требования указать:

- статус реализации: `реализовано`, `частично реализовано`, `не реализовано`, `реализовано с отклонением`, `невозможно подтвердить` или `не применимо`;
- файлы, символы и объяснение поведения;
- выполненные проверки и изученные статические доказательства;
- достаточность доказательств: `достаточно`, `частично` или `недостаточно`;
- непокрытые ветви и ограничения.

Успешная команда или существующий тест не доказывают полный критерий автоматически. Объяснить, почему совокупность доказательств достаточна.

### Реестр изменений

Для каждого изменённого файла указать repository, path, тип изменения, связанные Requirement IDs или техническое обоснование, статус рассмотрения и проверенные владельцы/получатели. Пустой diff фиксировать на уровне manifest.

### Замечания

Дефект существующей реализации содержит приоритет, Requirement ID или нарушенный контракт, минимальный диапазон строк, достижимый сценарий и последствие.

Пробел реализации содержит Requirement ID, ожидаемое поведение, доказательство отсутствия, предполагаемого владельца и последствие; ссылка на несуществующую строку кода не требуется.

Приоритеты: `P0` — катастрофический эффект; `P1` — блокирующий основной сценарий или серьёзная регрессия; `P2` — значимый дефект в конкретных условиях; `P3` — небольшой подтверждённый дефект.

## Порядок отчёта

Первым элементом без вводного текста вывести:

```markdown
# <ПРОХОДИТ ПРОВЕРКУ | НЕ ПРОХОДИТ ПРОВЕРКУ | ПРОВЕРКА НЕ ЗАВЕРШЕНА>

Причина: <одно предложение с решающим основанием>.
```

- `ПРОХОДИТ ПРОВЕРКУ` — все применимые требования реализованы, доказательства достаточны и подтверждённых дефектов нет.
- `НЕ ПРОХОДИТ ПРОВЕРКУ` — найден подтверждённый дефект, отклонение либо нереализованное требование.
- `ПРОВЕРКА НЕ ЗАВЕРШЕНА` — без доказанного дефекта реализацию невозможно оценить из-за отсутствующего описания задачи, обязательного вложения или доступного для анализа diff.

Для отрицательного результата выбрать наиболее серьёзное замечание и указать Requirement ID, если он применим. Для незавершённой проверки назвать конкретный отсутствующий вход или доказательство. Для успешной проверки использовать основание «все применимые требования реализованы, подтверждённых дефектов не найдено».

Далее вывести:

1. Замечания по убыванию приоритета либо «Доказуемых дефектов не найдено».
2. Источники.
3. Покрытие требований.
4. Изменения вне требований.
5. Выполненные проверки.
6. Ограничения проверки с точными проверенными base/head SHA либо «нет».

Завершить отчёт блоком:

```text
Итог: <ПРОХОДИТ ПРОВЕРКУ | НЕ ПРОХОДИТ ПРОВЕРКУ | ПРОВЕРКА НЕ ЗАВЕРШЕНА>.
Основание: <одно предложение>.
Ограничения: <список либо «нет»>.
```

Верхняя `Причина` и финальное `Основание` должны описывать один решающий факт.

## Приоритет вердикта

1. Если найден доказанный дефект, отклонение, частично реализованное или нереализованное требование, использовать `НЕ ПРОХОДИТ ПРОВЕРКУ`, даже когда часть проверки недоступна.
2. Если дефект не доказан, но отсутствует минимально необходимый вход, обязательное требование невозможно подтвердить или diff нельзя построить и исследовать, использовать `ПРОВЕРКА НЕ ЗАВЕРШЕНА`.
3. Если все применимые требования реализованы с достаточными доказательствами и подтверждённых дефектов нет, использовать `ПРОХОДИТ ПРОВЕРКУ`; необязательные непроведённые проверки перечислить как ограничения.

Недоступность remote сама по себе не меняет вердикт, если проверены точные base/head SHA и diff доступен. Пустой успешно построенный diff не означает незавершённую проверку: отсутствие требуемой реализации ведёт к `НЕ ПРОХОДИТ ПРОВЕРКУ`.

Если требование уже выполнено вне diff, оценивать это только в пределах явно согласованного scope. Доказанный дефект имеет приоритет над любыми ограничениями.
