# Task Code Review

Проводить доказательное ревью реализации относительно требований. Не изменять код, рабочее дерево, локальные ветки, историю, требования или вложения.

Сообщать только доказуемые дефекты и пробелы реализации. Подтверждать кандидатов исходным кодом, указывать достижимый сценарий и последствие, исследовать определения и релевантных получателей изменённого поведения. Существование теста или успешная команда сами по себе не доказывают полный критерий.

## Выбрать режим

- Если `mode` отсутствует или равен `coordinator-review`, прочитать [правила полного ревью](references/coordinator-review.md) и отвечать за весь scope и итоговый вердикт.
- Если явно указан `mode=delegated-review`, прочитать [правила делегированного ревью](references/delegated-review.md). Применять этот режим только к переданному review packet.

Роль субагента сама по себе не выбирает режим. При явно запрошенном `delegated-review` и невалидном packet вернуть `scope_status=blocked` с перечнем отсутствующих или невалидных полей. Не переходить в полное ревью, не выполнять remote query или fetch и не расширять полномочия.

## Условные правила

- Если доступны Node и `scripts/review-tools.js`, прочитать [правила автоматизированного fast path](references/automation.md). При недоступности использовать ручные правила выбранного режима.
- При продвижении base после merge base, частичной интеграции, rewrite, revert, историческом риске или запросе на аудит истории прочитать [правила истории и интеграции](references/git-history.md).
- При изменении публичных API, форматов, схем, сериализации, persistence, config keys, feature flags или межрепозиторных контрактов прочитать [правила семантической инвентаризации](references/semantic-inventory.md).
- Перед запуском тестов, сборки, линтеров, генераторов или других проверочных команд прочитать [правила безопасной верификации](references/safe-verification.md).
